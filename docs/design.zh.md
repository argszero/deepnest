# deepnest 设计

**状态：v1 的设计定稿。** 这份文档就是写代码所依据的可执行规格。凡与它冲突之处，以宿主的决定记录为准；下面每条决定都标注了出处。

全文使用的出处标记：

- **`宿主 HH:MM`** —— 宿主 2026-10-30 在该时刻拍板，不再翻案。
- **`实现自决, ref: <路径>`** —— 写这份文档时确定，并指明 EMRG 中作为先例的代码。若那段代码给出的论据相反，可以改。

---

## 1. v1 是什么

本地优先的应用生成器：一个自包含的二进制（约 140 MB），双击后在浏览器打开页面；每个生成出来的应用是一个目录加一个专属 agent。**v1 一次交付约定的全部边界**（`宿主 20:42`），不是先做最小闭环、后续补。

三个平台同时出：macOS arm64、Windows x64、Linux x64（`宿主 20:56`）。平台后端从第一行就抽象，共享代码里不许有 macOS 形状的假设。

## 2. 进程拓扑

**只有一个监听端口，其余全部内部化**（`宿主 20:45`）。

```
浏览器 ──► 127.0.0.1:4270  （唯一对外暴露的端口）
              │
              ├── /                     控制面板
              ├── /app/<slug>/          应用 <slug>，转发
              └── /api/…                控制面板自己的接口
                      │
                      └──► 127.0.0.1:<临时端口>   应用自己的服务
```

- 应用真实监听的端口每次启动重新分配，不出进程、不对外、不稳定、不持久化。
- 转发层往每个 `/app/<slug>/` 的响应里注入悬浮球，所以 agent 把应用页面整块重写也不会把它弄丢；为此它也改应用设的 CSP。
- 因此转发层负责：注入 `<base href>`、重写绝对路径、重写 `Location` 头、给 Cookie 加 `Path` 前缀、WebSocket 升级、SSE 不缓冲。

单实例准入**就是那个 bind 本身** —— 内核拒绝第二个 bind，所以没有可伪造的 PID 文件、没有竞态（`实现自决, ref: emrg/server/daemon.py::_create_fixed_port_socket`）。POSIX 只设 `SO_REUSEADDR`、绝不 `SO_REUSEPORT`；Windows **不设** `SO_EXCLUSIVEADDRUSE` —— 两个都不设的默认行为本来就以 `WSAEADDRINUSE` 拒绝第二个 bind，而显式设置要走一次原始 winsock 调用，那是打包期该做的事，不在这一层声称。bind 失败但后面没有活着的监听者 ⇒ TIME_WAIT 残留，有界重试，不要直接失败。

随机令牌写入 `~/.deepnest/deepnest.token`（权限 `0600`），并由 keepalive 定时重写，外部误删能自愈（`实现自决, ref: emrg/server/daemon.py::serve`）。回环地址不是安全边界：令牌加 `Host`/`Origin` 校验才是挡 CSRF 与 DNS rebinding 的东西。

**二进制目前服务的路由**（`实现自决`，2026-10-31）：`GET /` 面板（`crates/web`：已配置的端点或没配置、盘上每个应用与「这里不是应用」的目录、端点表单、新建应用表单、每个应用的五个动作、加载器找到的用户级 skill 与它拒掉的条目，脚本关掉时这些事实仍在标记里）、`GET /panel.js` 面板自己的脚本（走路由而不是内联，`/` 才能用 `script-src 'self'`：从文件系统进页面的字符串成不了代码；页面把控制令牌放在 `<meta>` 里 —— 本机进程本来就能读那个 `0600` 文件，这样用户不必为了打开自己的面板去粘贴密钥）、`GET /api/health`（唯一免令牌，它不带用户数据）、`GET|POST /api/config`（端点；`GET` 只说配没配、模型叫什么，绝不回密钥；`POST` 是首启表单，也是读请求体的三条路由之一 —— 密钥放进 URL 就进了浏览器历史与一切记录 URL 的日志，这也是令牌走头不走路径的同一个理由；body 有上界 `MAX_BODY`（16 MiB，且是按 chat 路由自己公布的那份图片额度定的，不能比它小）且只认声明了 `Content-Length` 的；落盘走 `config::save`：`0600`、原子写、且先过二进制启动时那套校验，所以它启动会拒绝的值由表单先拒掉；进程立刻生效，别处没有缓存，不必重启）、`GET /api/apps`、`POST /api/apps/<slug>/create|build|start|stop|restart`。`create` 回 `201` 并带上目录与文件清单 —— 客户端的下一个问题永远是「写到哪了」；`build` 是慢的那个，它跑工具链、热缓存也要几十秒，并占住发起它的那条连接。另加三条：`POST /api/apps/<slug>/chat`（一个轮次交给该应用的 agent；body 是 `{"message": "…"}` —— 用户打的字不该进 URL，那会被写进浏览器历史和一切记录 URL 的日志；它不认控制令牌，认一张只够得着这条路径的 cookie，因为发它的悬浮球就住在应用自己的页面里，写在那儿的令牌应用的脚本一样读得到；三道拒绝各指一条下一步：体不是一条消息 `400`、没有配置文件可读 `503`、配置里还没有模型 `412`）、`GET|POST /api/apps/<slug>/escalation`（轮次正在等的问题，以及它的回答：`GET` 回 `{"pending": …}`，没人问时是 `null`，否则是应用、申请的档、会话此刻的档和模型给的理由；`POST` 收 `{"approve": false, "reason": "…"}`，没有轮次在等就回 `409` —— 让页面以为自己答上了，等于告诉用户他批准了一件从未发生的事；它有自己一张 cookie，与 chat 那张分开铸、各管各自路径，所以「花掉一次 agent 轮次」的能力回答不了一条提权申请）、`GET /api/skills/updates`（有没有已装的 skill 发布了更新版：状态文件里每个允许刷新的 skill 一个答案。走控制令牌，且**故意不**进 `/` 的渲染——这条检查是每个 skill 向别人的服务器发一次请求，同步渲染它会让一台断网的机器挂住它本想打开的那张面板；页面先把本地那份渲出来，这一份晚一拍由脚本自己取进标记里已有的那一节）、`GET|POST /api/skills/refresh`（更新检查的答案落到的那一步：`POST` 带 `{"name": "…"}` 跑该 skill 自己的包、重写它发布的那个文件，再把 release 检查采纳的版本记进状态文件；`GET` 回上一次刷新落到了哪。它回 `202` 而不是 `200` —— 发布者是那个包、什么时候返回由它自己决定，比浏览器肯等的一次请求长得多 —— 所以页面轮询同一条路由；一次刷新在跑时再问回 `409`，因为状态文件是一个文件、两个写者会丢掉其中一条记录。走控制令牌，且必须是 `POST`：它会在用户机器上跑一个程序）、`GET|HEAD /app/<slug>/…` 转而由**转发层**送到应用此刻的回环端口。它不走令牌：这是浏览器点开的那张页面，而一条要求 `Authorization` 头的链接等于一条打不开的链接；约束它的是「它只够得着本机上这个应用自己的端口」。没在跑的应用回 `503` 并点名启动它的那条 `POST`；在状态检查与连接之间消失的回 `502` 并给出应用日志路径；slug 不是应用的回 `404`。对应用发 `POST`/`DELETE` 一律 `405` 加 `Allow: GET, HEAD` —— 这一层不携带请求体，把没有内容的请求转过去等于告诉应用「来了个请求」，而它什么都没说。其余未知路径 `404`。`POST` 用于状态变更 —— 浏览器会预取 `GET`，藏在 `GET` 后面的状态变更就是拖一下链接就发生的事。本版本的 HTTP 层读**四条**路由的 body（`/api/config`、`/api/skills/refresh`、`/api/apps/<slug>/chat`、`/api/apps/<slug>/escalation`）；其余路由带上 body 一律回 `400` 并点名这四条 —— 看不见内容的请求不能回「已完成」；chunked 回 `411`（没有声明长度就没有上界），声明长度超过 `MAX_BODY` 回 `413`。

**面板由二进制在默认浏览器里打开**（`实现自决`，2026-10-31）—— README 第一句「双击运行，打开浏览器里的一个页面」的后半句。五件事：**不引依赖**，三平台各一个程序 —— macOS `open`；Windows 经 `cmd /C start`，空标题参数不能省（不传它，`start` 会把 URL 当成窗口标题，什么都不打开）；其余平台 `xdg-open`；包一层三个命令行换来的只是一份要审的依赖。**在 banner 之后、bind 之后**，本次运行要说的话（地址、配置与令牌路径、日志、工具链）先打印并 flush 再问桌面，而监听此时已在接受连接，浏览器落到的页面是服务好的而不是抢跑的。**第二个实例打开它找到的地址** —— 双击两次要的就是那张已经在服务的页面，把地址打到没人看的终端里等于第二次点击什么都没发生。**打不开只算一行、不算启动失败** —— 面板是这个程序的全部界面，桌面不接 URL 不该把界面一起拿走；地址照打，失败的那个命令按人会打的样子写出来（`cmd /C start`，不是 `cmd`）。**开关是 `--no-open`，打开器是一条可注入的缝** —— 端到端测试起的是真二进制，不传这个开关就会在跑测试的机器上开一个浏览器窗口，CI 上一开就是三个平台。

## 3. 数据布局

```
~/.deepnest/
├── config.toml              模型端点：base_url / key / model      （宿主 20:18）
├── deepnest.token           0600，控制面板令牌，每次运行重写
├── skills/<name>/SKILL.md   已安装的 skill                        （宿主 20:26）
├── skills/.state.json       managed: true 才允许更新器刷新
├── toolchain/               解包出来的 Rust 与 bun，首启原子解包
├── apps/<slug>/
│   ├── src/                 应用自己的源码
│   ├── app.sqlite           WAL、busy_timeout、单写者
│   ├── target/              编译产物
│   └── .agent/
│       ├── history.jsonl    对话，逐轮可重放
│       ├── llm.jsonl        每次请求发了什么、回了什么，含花费
│       ├── llm.jsonl.1/.2   留在旁边的两份轮转
│       └── memory/*.md      长期记忆 + MEMORY.md 索引
└── logs/
```

两条规矩在这里很重：

- **agent 的状态放在应用目录内部**，于是删应用就一起删掉它的对话与记忆，备份应用也一起备份（`宿主 20:58` —— 记忆属于「EMRG 同等能力」，不是可选功能）。
- **一次请求花了多少，记在对话文件旁边而不是里面。** `history.jsonl` 说说了什么，`llm.jsonl`
  说每次请求带了什么、端点答了什么、收了多少 —— 三者互相都推不出来。token 数无法从文本反推；
  同一段历史每轮重放都要再收一次钱；而循环自己缩小重发掉的 `400`，在一个恢复了的对话里不留任何
  痕迹。这份日志是诊断用的：写不进去也照常跑，超过 50 MB 轮转保留两份 —— 因为一条请求记录带着
  它发出去的整段上下文。
- **agent 的对话不存进 `app.sqlite`。** 那个库属于用户的应用，第二个写者正是 WAL 实测里已经记下的 `database is locked` 故障。

## 4. 模块

每个模块是一个 crate，自带测试。上层不伸手进另一个模块的内部。

### `crates/llm` —— 模型访问 `（宿主 20:18）`

对用户给的 `base_url` + `key` + `model` 说 OpenAI 兼容协议。流式、退避重试，以及**不把 400 误判成上下文过长**的错误降级 —— 这个坑 EMRG 踩过，不许再踩一遍（`实现自决, ref: emrg/server/llm.py`）。没有厂商分支。

### `crates/sandbox` —— 一套策略与两个执行者 `（宿主 19:03、19:05）`

三档：`read-only`、`workspace-write`、`danger-full-access`。围栏是**操作系统级**的，不是进程内查路径：macOS 用 Seatbelt、Linux 用 `bwrap`、Windows 用 ACL 加受限令牌。

同一个函数 `writable_roots()` 同时喂给文件工具的拒绝口和 OS 策略，所以两者不可能给出两个答案（`实现自决, ref: emrg/sandbox/roots.py`）。可写面恰好是：应用目录、工具链目录、临时目录。

提权是**跳表、一次一跳、逐次批准**：工具调用携带申请的档位与理由，宿主在网页上批准，会话默认档不动。`read-only` 可一跳直达 `danger-full-access`；`danger-full-access` 无处可去；不构成放宽的申请直接拒，而且是在问宿主之前就拒（`实现自决, ref: emrg/sandbox/escalation.py`）。申请经由 `GET`/`POST /api/apps/<slug>/escalation` 抵达人 —— 轮次等待期间悬浮球轮询的就是这条。

受保护文件在任何档位都不可写，判定按设备号+inode 而不是字符串比较：`config.toml`、`deepnest.token`、skill 状态文件（`实现自决, ref: emrg/sandbox/policy.py::same_file`）。

Windows 后端在体量上远超其它两个（EMRG：ACL、FFI、受限令牌、spawn 合计约 3.2k 行）。`windows` crate 省掉的是手写 FFI，不是 ACL 与令牌的逻辑。排期按这一块估，不按平均值估。

**现状，就写在计划旁边：** `WindowsAcl::plan` 已经能推导出 ACL 计划，`available_backend` 也会返回它，但**施加者**——真正写 ACE、建受限令牌的那段代码——还没写。所以 Windows 上受围栏的命令由 `BashTool::plan` **拒绝**，报错原话就是这一点；它不会被改成不受围栏地跑。这正是 fail-closed 该有的样子，也是 Windows 下载与 macOS 下载之间唯一的缺口：文件工具、应用构建与应用运行都不走那条路径，正常工作。

### `crates/command_scan` —— 围栏看不见的那一层 `（宿主 19:03）`

命令文本扫描器，守两类东西：读方向的外泄，以及围栏无法表达的那一条禁令 —— **agent 不许停掉或重启 deepnest 自身**。做法是切词、展开嵌套命令、识别 wrapper（`eval`、`-exec`、`builtin cd`），再判断某个词是否处于命令位（`实现自决, ref: emrg/tools/command_scan.py`）。

### `crates/tools` —— agent 的手 `（宿主 20:20）`

`bash`、`read`、`write`、`edit`、`glob`、`grep`、`subagent`、`install_skill`、`app`。不是精简子集：宿主定的是每应用 agent 具备接近完整的 EMRG 能力，包括启停这个应用、看日志、操作浏览器、截图。后两条**来自 browser-harness skill，不由核心内建**（`宿主 20:23`，`宿主 20:48` 再确认）—— 核心只负责在默认浏览器里打开应用页。

**应用自己的生命周期就是 `app`**（`实现中决定`，2026-11-02）：一个工具带 `status`、`start`、`stop`、`restart`、`logs`，最后那个读应用的日志或上一次构建的日志。上面那段在集合里还没有它的时候就先许下了这项能力，而补上这个缺口的不是 skill：skill 是一份 `SKILL.md`，描述的是已经存在的工具，而进程表是守护进程的。绕道也能到，但是错的那种到法：面板自己那些生命周期路由由控制 token 把守，而那份文件是任何模式都**不能写**的三份之一 —— 不能写，不等于不能读 —— 所以 agent 可以 `read` 它，再用 `bash` 去调那些路由。可那时到手的只是 shell 的输出：一次拒绝、一次超时、一次成功的启动，看上去都是需要解读的文本，这一轮汇报的是它推断出来的东西，而不是监管器知道的东西。**这次调用不点名应用**：工具是为某一应用的某一轮构造的，它握着的监管器已经绑死那个 slug，所以没有可以指错对象参数。读（`status`、`logs`）在每个模式下都放行；改（`start`、`stop`、`restart`）在 `read-only` 下按围栏一贯的说法被拒，并点名该申请哪个模式。

其中三个是**缝而不是叶子**，理由都是它们委托的那件事住在它不能依赖的 crate 里：`subagent` 要一个子循环（`crates/agent`），`install_skill` 要目录、状态文件和发布器（`crates/deepnest`，只有它知道 home 在哪），`app` 要一张进程表和那个 `logs/` 在它底下的 home（`crates/deepnest` 与 `crates/apps`）。没人注入就不提供 —— `registry::all` 是六个叶子，`registry::with_seams` 每个缝能兑现哪个就加哪个，都不给就一个不加 —— 所以模型被告知的集合，永远是调度器跑得动的集合。

shell 结果明确携带沙箱判定，区分「runner 没起来」与「沙箱拒绝」，超时杀进程组，被拒时追加提权提示（`实现自决, ref: emrg/tools/bash_tool_v2.py`）。

### `crates/agent` —— 工具循环

轮次循环、流式拼装、工具派发、对话持久化、记忆写入。记忆分两层：`history.jsonl` 存对话，另一层是带 frontmatter 的 Markdown 条目加一个 `MEMORY.md` 索引（一行一条，退休改 `status` 不删）。进提示词的只有索引，正文由 agent 用 read 工具自己读（`实现自决, ref: emrg/memory.py`、`emrg/session.py`）。

系统提示词**重写一份**。agent 的行为质量大半在这份上，EMRG 的不能照抄 —— 但 EMRG 已经付过学费的三处故障可以便宜地避开：压缩按字符数而不是按条数、工具循环在轮次取消时能停下、400 不被当成上下文过长。

**agent 已经进二进制，能回一条消息了**（`实现中决定`，2026-10-31）。`POST /api/apps/<slug>/chat` 从请求体读 `{"message": "…"}`，回一个轮次。先有三道拒绝，各指一条不同的下一步：体不是一条消息（`400`）、进程没有配置文件可读（`503`）、配置里还没有模型（`412`，首启表单只差一个请求）。此后 `crates/deepnest::chat` 为**每个应用拼一个 agent** —— 六个叶子工具跑在该应用的 `workspace-write` 策略上、对话与记忆在 `<应用>/.agent/` 下、系统提示词由真加载器给出 —— 交给循环。接线带出五条决定：

- **HTTP 适配器两种 scheme 都走，而且互不降级。** `crates/gateway::transport` 为 `http://` 用裸 `std::net::TcpStream` 实现 `deepnest_llm::Transport`，`crates/llm` 依然不拥有 socket、依然无网络可测；`https://` 走 `native-tls`，把信任决定交给平台（macOS 的 Security framework、Windows 的 SChannel、Linux 的 OpenSSL），于是一个端点按用户浏览器用的**同一个证书库**校验。选那个库、而不是把根列表打进二进制，理由就是这一点：公司代理的证书签发机构装在那里，内置列表会拒绝它，而用户只会读到「deepnest 坏了」。`HttpTransport` 是两者合体，也是二进制实际装上的那个；两半各自点名拒绝对方的 scheme，因为明文撞 TLS 端口要么是静默、要么是把 key 明文发出去，两者都不是「回退」。**被拒的证书要说清是哪一种拒绝**（`实现中决定`，2026-11-01）：证书不受信任、证书是给别的名字的、端点根本到不了 —— 三种情况三种修法，所以是三条消息；`native-tls` 不暴露错误码、只给一句话，所以这个区分是从那句话里读出来的，而平台自己不说清名字不匹配的地方，消息仍然说「证书被拒」，绝不退回「连接失败」。**适配器现在做流式**（`实现中决定`，2026-11-01）：`post_stream` 边读边解 —— 分块体增量去分块、声明了长度就照长度收、两样都没有就读到连接关闭 —— 并且把每个完整的事件在**索取下一批字节之前**交给调用方，于是「模型中途停顿」是调用方看得见的一次停顿，而不是它必须默默等完的一段。这条规则还带出两件事：文字只在**完整**之后才喂给解码器，因为一个字符被拆在两次读之间，对中文回答来说是常态而不是意外；非 2xx 的响应**整段读完**，因为拒绝是一份文档，必须和整段那条路给出完全一样的分类。
- **只有要求看的人才会看到轮次被写出来。** `crates/deepnest` 的 `model::Endpoint` 用 `Client::chat_stream_with` 服务 `Model::turn_with`，于是答案的每一片在模型还在写的时候就到了正在画它的那一方手里；循环只通过 `Agent::run_turn_watched` 走到这道缝，`run_turn` 是同一条循环配一个丢掉一切的观察者。**原来剩下的两步都已落地。** `POST …/chat` 默认仍回一个 JSON 体，除非请求的 `Accept` 点名 `text/event-stream`：那时头在轮次开始之前就写出去，答案的每一片是一个事件，最后一个事件携带的正是整段那条路会回来的那份回复。**拒绝永远不是流** —— 路由服务不了的请求照样用一个 body 回答，因为页面拿到事件流的第一件事是解析它，而一次以解析错误形式到达的失败，是一句什么也没说的失败。**页面两种都读**（`实现中决定`，2026-11-01）：对话框要求流，然后按**回复自己的** content type 决定怎么读，而不是按它要求了什么，所以 `401` 或 `412` 仍然是那句「该怎么做」的话。每一片在轮次还在写的时候就追加到框下面那一行 —— 这正是「一轮很长」与「一轮卡住了」的区别，而行尾的一个标记是唯一说明「还有下文」的东西。逐词生长的一行不逐词播报；答案完整时 live region 才重新打开。没有收到收尾事件就结束的流会说明连接断了并指向转写，因为那是关于**这次阅读**的事实，不是关于轮次的。

- **只发了一个调用的一轮，在下一轮做决定的地方被提醒一次**（`实现中决定`，2026-11-04）。规则本身 —— 一轮要么不调用，要么五个以上 —— 留在提示词里，但同一个 provider 上的兄弟 agent 实测过它的衰减：提醒后那一轮五个，下一轮两个，第四轮又回到一个。提示词做不到的事循环做得到，因为它知道上一轮到底发了几个。于是上一轮恰好一个调用的请求，末尾多一条 `{"role": "system", "content": "batch call"}` —— 是 **system** 不是 user：内容是给模型读的，角色是给其余所有读者读的，而 user 回合是「人说的话」，在转录里、在页面上、在压缩摘要里都是。随之还有三条：**「上一轮」从对话末尾读出来**，不用循环变量记，因为变量一交回就丢，而每轮都交回的回合正是最需要省的那一个 —— 与 `Session::owed` 从文件里读「欠什么」是同一个理由；**提醒从不进对话**，每一轮的请求都从 `messages` 重新派生，所以它既不会被重放、不会累积，也不会被画成人说过的话（模型日志照记，日志才是「实际发了什么」的账）；**只给了一个工具的回合不提醒**，那条规则它守不了，守不了的提醒等于让它把同一个工具调两次。
- **端点每请求读一次，不在启动时握住。** `POST /api/config` 能改它，启动时拼一次的 agent 会一直问旧的，直到下次启动。
- **改过东西的轮次只报 `changed`，不顺手重编译。** 是 `bash` 与 `write`/`edit` 置这个标记，回复带着它，编译仍旧是既有的 `POST /api/apps/<slug>/build` 加 `/restart`。在这个请求里编译会让一条连接卡在 `bun install` 上一分钟，比任何浏览器肯等的时间都长。
- **被拒是用户该改的东西，不是本机出错。** `Refused` 回 `422`，模型够不到回 `502`，对话文件写不了回 `500` —— 三条不同的下一步，所以三个不同的状态码。

### 应用自己的 agent —— 声明出来，由应用自己驱动（`实现自决`，2026-11-03）

以上说的都是每个应用**一个** agent：对话框那个，写应用的那一个。应用还会**用**一个 —— 飞书桥要判断哪些消息需要处理，待办应用拿到一条转过来的消息要弄清它到底在问什么 —— 这些回合属于应用，不属于坐在面板前打字的人。形状是四件事：

- **应用在 `deepnest.toml` 里声明自己的 agent**，一表一个 `[[agent]]`：`name`（slug，因为它同时是 URL 段和目录名）、`prompt`（追加在 deepnest 自己的规则**之后**，绝不替换 —— 能替换提示词的 manifest 就能靠「换一种说法」把围栏关掉）、`workdir`（在哪干活、能写哪）、`skills`（额外的技能目录）、`tools`（应用自己 MCP 端点的路径，通常 `/mcp`）。`create` 会往每个新应用里写一个，名字与它自己代码里调用的常量一致 —— 第一次要回合就被「没声明这个名字」拒掉的应用，看起来就是坏的。
- **应用用启动时拿到的票据调 `POST /api/apps/<slug>/agent`。** 它需要的全部就是三个环境变量：`DEEPNEST_URL`、`DEEPNEST_APP_TICKET`、`DEEPNEST_APP_SLUG`。票据（[`ticket`]）按应用、按启动签发，只开三条路由 —— `agent`、`agent-result`、`tools` —— 管机器的一条都不开。请求体是 `{"agent","message","session","images","tools"}`；`session` 是应用自己给一段对话起的名字，`images` 是与 `/chat` 同一个字段、由同一个读取器读的图片（应用自己的窗口也发它），`tools` 是应用的能力声明，用 MCP 的 `tools/list` 形状。
- **回合可以暂停，而这正是设计。** 应用在问这个回合时，自己正处在一个请求里面。所以应用自己的工具**不能真去调** —— 一次只答一个请求的服务端，没法在一个还没结束的请求里回应回调，而等待发生在另一边，这一边加并发救不了。于是一轮里能在这边跑的全都跑掉，剩下的写成 `PendingCall` 交回，回合结束（`TurnOutcome::Paused`）。应用在自己进程里跑那些调用，把**每一条**答案 POST 到 `agent-result`，那个请求从同一个文件继续**同一个回合**。一轮 = 一次交回，正是提示词早就教给模型的批调用规则，从另一边看。
- **暂停状态不落在这个进程里。** 欠什么在 `history.jsonl` 里看得见 —— 有调用、后面没有答案 —— 所以交回与答回来之间崩掉的应用，能从 `Session::owed` 把同一份清单读回来；被交回又没人答的回合，会在下一个回合开场前关掉，而不是把之后每一个请求都毒死。

四条随之而来的决定：

- **交回是「谁在等」的属性，不是工具的属性。** [`deepnest_tools::DeclaredTool`] 的 `runs_here()` 是 `false`，它的 `call` 会拒绝；但一轮要不要**停在那里**由 `Agent::handoff` 决定，默认关、这个模块建的回合开。对话框那个回合一点没变 —— 它在本地跑工具，因为身后没有请求被握着 —— 应用的回合才暂停。只做成工具上的标志，会让对话框把一个没人接的答案交回给页面。
- **应用的工具随请求过来，不靠回调去问。** 在应用正等着的回合里去问它的 `tools/list`，就是暂停要防的那种嵌套调用，只是早了一层。应用自己说它能干什么，回合据此建起来。
- **没声明的名字在找模型之前就被拒。** 拼错是应用作者要修的，端点缺失是这台机器的，所以带「它到底声明了哪些」的 `404` 排在关于配置的 `503` 前面。
- **第三方 MCP server 照旧直接调用。** `crates/tools::mcp` 是那种「跟当前请求毫无关系」的 server 的客户端 —— 没有人在等它，调它就是这一轮干的活。两条路不同，因为另一头本来就不同。

这一版**不做**的：把应用的对话画进对话框的转录。应用的 agent 把自己的历史放在 `<app>/.agent/agents/<name>/`，带自己的 `llm.jsonl`；面板的转录是对话框的，混进来就是把人没要过的机器回合摆在他面前。

**应用还得有一个能跟它说话的窗口**（`实现自决`，2026-11-04）。应用声明了 agent，人不画一个聊天窗就永远碰不到它；而让应用作者 —— 或者写这个应用的模型 —— 从零画，画出来的就是面板里已经失败过一次的那个窗口：用工具的一轮跑一分钟而屏幕上一片空白、刷新就丢对话、没有停止键。所以窗口由 deepnest 出：`/agent-chat.js`，应用自己写一行标签就打开 —— 而那一行加载的是 `/dialog.js`，也就是站在应用页面旁边的那同一个对话框。

六条随之而来的决定：

- **一个窗口，两个通道。** `crates/web/src/agent-chat.js` 是个初始化器：它把应用声明的 agent 名字写进 `window.deepnestDialogTarget`，然后加载 `crates/web/src/dialog.js` —— 唯一的渲染器。它取代的那个第二窗口是 471 行、对着对话框的 3,646 行，而且没有压缩提示、没有授权请求、没有截图：三个还没人写过第二遍的能力，旁边那一份却三个都有。通道只改一条路由和一个请求体，别的都不改：`/chat` 带图片与文件，`/agent` 带 agent 名字、随话发来的图片与应用自己的工具；两边都经同一个读取器读同一份 `history.jsonl`，所以线格式上的回合是同一个形状，两边也都用同一个 `event: text` … `event: done` 流回答一轮。对话抽屉两个通道都有：`sessions` 是一个按根目录取的存储（应用自己的 `.agent`，或某个声明 agent 的目录），所以应用自己的窗口带上 agent 名字问的是同一条路由、画的是同样的行 —— 同样的文件、同样的指针、同样的命名，只有一份实现。应用窗口没有路由的控件只剩构建监视一个，它是被条件挡掉的，不是画出来再被拒绝。截图不在其列：`/capture` 回的是一条 `data:` URL，而 `data:` URL 就是图片，图片两条路由都带，所以两个通道都画这个按钮。剩下的只有文件 —— 它的内容只有 `/chat` 会写进提示词 —— 于是在放下它的那一刻就说清楚，而不是等它看起来已经附上之后。
- **窗口是应用 include 的文件，不是应用抄走的代码。** `/agent-chat.js` 是与模型已经写过的每一个应用之间的契约，所以它的路径是 [`deepnest_web`] 里的常量，而不是模板里的字面量 —— 抄进应用的那一份，就是以后不再被修的那一份。`data-agent` 说明它跟这个应用声明的哪个 agent 说话；不写就什么都不画，并说出来 —— 猜比让应用作者写清楚更糟。
- **三条路由，页面里不放任何凭证。** 窗口用 `GET /api/apps/<slug>/agent?agent=<name>` 读对话，同一条路径 `POST` 发消息，`POST /api/apps/<slug>/cancel` 停止。它自己不拿 token：浏览器自带的是网关在交付应用页面时种下的 cookie。`DEEPNEST_APP_TICKET` 绝不能进页面 —— 那是应用进程的凭证，拿到它的页面能花掉这个应用所有的回合。
- **`agent` 是浏览器唯一能调的应用 agent 路由，所以它是唯一上 cookie 名单的。** [`grant::AGENT_COOKIE`]，由种对话框 cookie 的同一个循环种下，作用域就是那条路径：能朝应用的 agent 发消息的页面，没有道理去够 `agent-result` 或 `tools`；用第二个名字把这件事写出来，好过让读者自己发现一个 cookie 被两种身份共用。
- **调用方要流就给流，不要流就给一整块。** 应用自己的进程正是不要流的那种：它发了一个请求，等一个结果回去继续。浏览器用 `Accept: text/event-stream` 要，回合进行中收到 `text` 事件，最后是 `done` 或 `error` —— `/chat` 早就是这个形状。同一条路由两种回答，因为回合是同一个回合，只是观众不同。
- **`GET` 读对话，`POST` 占住一条对话。** 读哪一段是查询参数，因为只能靠 `POST` 才读得到的转录，等于一个页面必须假装发了点什么才能看自己刚说过的话。同一个路径换一个动词就是发一个回合，所以 `GET` 永远不是；`agent-result` 走 `GET` 回 `405`，写明该用哪个方法 —— 对象是能打开它的那些调用方（令牌或应用票据），页面的 cookie 只开 `agent` 这一条。

为此网关有一处跟着动：`connect-src` 与被放行的 `script-src`、`style-src` 并列，一起加进被注入页面的策略里。窗口属于应用自己的页面而不是 stage 页，所以一个写了 `default-src 'none'` 的应用，否则会得到一个画得出来却什么都说不出的窗口 —— 与这套策略改写本来就在防的静默失败是同一种，只是更晚一步。它不多给页面任何它本来没有的东西：那次 fetch 要花的 cookie，本来就是给这个页面签的。

窗口本身照面板那套规矩来：每一段文字都以节点插入，绝不作为标记；一批调用中途暂停的回合显示为仍未完成，而不是画成已经答完；失败显示在引起它的那一行、在窗口里，不吞掉。

### `crates/skills` —— Anthropic Agent Skills

加载器读两个根目录（`~/.deepnest/skills/`、`<应用>/.agent/skills/`）和两种布局（`<name>.md`、`<name>/SKILL.md`）；同名时应用级遮蔽用户级。渐进披露：进提示词的只有 `name` + `description` + `path`。没有 `description` 的文件不加载（`实现自决, ref: emrg/skills/loader.py`）。

**已落地的第一片：加载器**（`实现中决定`，2026-10-31）。`crates/skills` 读两个根、两种布局，返回提示词要用的那份列表。五条决定随之定下：

- **同一个根里撞名时目录布局赢，被顶掉的那个文件要报出来。** `<name>/SKILL.md` 是能带脚本与素材的那种布局，所以正在迁移过去的 skill 中途仍然可用。输掉的文件记成 `skipped` 条目 —— 用户改着 `notes.md`、而真正被读的是 `notes/SKILL.md` 时，他除此之外没有别的线索。
- **应用级遮蔽用户级，且不报。** 这是设计定的方向，也是有用的方向：一个应用若需要另一个 `notes` skill，不该逼它改用户那个的名字。遮蔽不是错，所以不产生 `skipped`。
- **不是可用 skill 的，一律连原因一起报出来。** 与 `crates/apps` 对待「不是应用的目录」同一种形状，理由也相同：只给一份列表的话，「还没有 skill」和「你 skill 的头部写错了」就是同一种读法，而后者用户唯一的线索只剩「提示词好像比预期空」。
- **符号链接只报不跟。** 跟了就等于让 skill 住在用户没放它的地方，而「这条是哪来的」恰是 skill 列表必须答得出的问题。
- **头部逐行读，缩进行是嵌套而非字段。** skill 可能带一个 `metadata:` 块，里面的 `description:` 不许覆盖顶层那个 —— EMRG 已经为此付过一次账（`实现自决, ref: emrg/skills/loader.py`）。逐行读还让结束分隔符是「一行」而不是「文中任意前三根短横」，描述里因此可以出现 `---`。

**现在已经接上，走的是提示词而不是路由。** skill 只通过系统提示词到 agent 手上，所以没有、也不该有一条 skills 路由：chat 这条路每轮调一次加载器，把 `name`、`description`、`path` 摆到模型面前。

**面板是用户读加载器结果的地方**（`实现中决定`，2026-10-31）。`GET /` 把加载器自己的答案渲染出来：一行说明 skills 目录与加载到几个，接着是每个 skill 的名字与描述，然后是它拒掉的每一条及其路径与原因。依旧没有 skills 路由 —— 为一张页面就要的事实开一条 API 没有道理。四条决定随之定下：

- **由服务端渲染，不是脚本去取。** 用户正是在改完一个 skill 文件之后打开这张页面，所以多一次往返恰恰就是藏住那次改动的那部分。这与应用列表的取舍相反，理由也正好相反。
- **只读用户级 skill，而且页面把这句话写明。** 调加载器时给应用的参数是 `None`：这张页面不属于任何应用，把所有应用的 skill 汇成一张列表等于宣称每一条处处适用。应用内部的 skill 在这里看不见是刻意如此，而这一点必须写出来，否则「我的应用里的 skill 怎么不见了」就是下一条针对刻意读法的 bug 报告。
- **`crates/web` 对 `crates/skills` 一无所知。** router 交给页面的是一行文字加两个 `(标签, 细节)` 列表 —— 与它原本就拿到的应用那一行同一种形状 —— 而页面在每个值写下去的那一刻转义它。skills 列表**最后**替换进页面，因为描述里的 `@@APPS@@` 是描述，不是「把应用数量再写一遍」的请求。
- **加载到的与被拒掉的是两张列表，而摘要那一句就是分界。**「还没有」与「没有能用的」是两张不同的页面：只有一条 skill、而它的头部写坏了的用户，得到的是「这一条不是 skill」加上原因，而不是「你没有 skill」。

随二进制内置的那份推荐目录本身就是一份普通 skill 文件，额外带一个 `skills:` 列表（`name`、`description`、`repo`、`install`、`dest`、`check`），`dest` 按 deepnest 自己的 home 拼写：`~` 即 `~/.deepnest`，`~/skills/` 正是加载器读取的目录 —— 写成字面的 `~/.deepnest/skills/` 会在 `DEEPNEST_HOME` 被迁移时落到没人读的地方。头两条是 `browser-harness` 与 `baoyu-design`（`宿主 20:26`）。安装状态在 `.state.json`：只有 `managed: true` 的条目允许更新器刷新，其余算宿主改过，永不动（`实现自决, ref: emrg/skills/installer.py`）。

**此后落地的第二片：内置目录与状态文件**（`实现中决定`，2026-10-31）。`catalog` 拿着内置的那份清单并把它读回来，`state` 记着哪些已安装的 skill 允许被刷新。四条决定随之定下：

- **目录就是一份普通 skill 文件，而这正是重点。** 加载器照常把它当 skill 捡起来，agent 因此看到一行「存在一份目录」；机器可读的部分是同一个头部里的 `skills:` 块，由已经在读头部的 `frontmatter` 读。另一条路——另起一种格式、自带 schema、自带读取器、自带提示词里的一行——是用一整套机制去说一个文件就能说的话，参照实现的 registry 就是那套机制（`实现自决, ref: emrg/skills/registry.py`）。
- **条目必须有 `name` 与 `description`，其余四个字段说的是「deepnest 会怎么抓它」。** 并非每个被推荐的 skill 都抓得到：`baoyu-design` 是一摞说明书、没有公开来源，所以它的条目没有 `repo`，目录把它称作**仅推荐**，而不是替它编一个来源。写了 `repo` 却没写 `install` 的条目是文件里的错误，要报出来——「我知道它住哪、不知道怎么把它弄来」是缺口，不是决定。
- **目录里没有任何一条会被静默丢掉。** 参照实现要求六个字段齐全、缺一个就跳过（`实现自决, ref: emrg/skills/registry.py`）；这里缺 `description`、有 `repo` 没 `install`、以及没有 `name`，各自是一条带原因的 `Rejected`，因为一条凭空消失的记录，与一份从来没有过它的目录，读起来一模一样。
- **`managed` 是唯一的闸门，而且失败时关着。** `State::managed` 是交给更新器的唯一一份列表，没有「全部 skill」的迭代器可以被误用；刷新一个非 managed 的 skill 是被拒绝而不是被悄悄升格；状态文件里没有 `managed` 字段的条目读作不可刷新，因为来源不明的文件不是许可；未知键在往返中保留，免得旧二进制删掉新二进制写下的东西。两个文件都是先写临时邻居再改名。

**内置目录是地板，不是真源。** `catalog::ensure` 只在该文件缺失时才写，覆盖的是全新安装与「升级后文件被删」两种情况，永不覆盖用户自己整理过的目录。

**此后落地：地板真的铺下了，目录也摆到页面上**（`实现中决定`，2026-11-01）。`home::prepare` 在 `prepare_home` 旁边调 `catalog::ensure`，`serve()` 调的是 `prepare`——启动本来就会跑的那一处。`ensure` 此前没有调用者，所以没被手工塞过这份文件的机器根本没有目录：每次刷新都被按名字拒掉「目录里没有叫 …… 的 skill」，而二进制自带的两个条目只存在于二进制里。`prepare` 写成函数而不是 `main` 里的两行，是为了让测试能在不启动服务器的情况下问「一次启动留下了什么」。四条决定：

- **面板列出目录里有、这个家目录里还没有的条目**，每条 deepnest 抓得到的都带一个安装按钮。条目不摆给人看，目录就只剩加载器那一行字来推荐它们，而那一行字是一句话，不是一个动作。
- **deepnest 抓不到的条目说明缺哪个字段，并且不给按钮。** `repo`、`install`、`dest` 逐个点名，手改目录时漏掉一个就是一行可修的东西而不是一桩悬案；那里放按钮，只可能去跑一件条目根本没描述过的事。
- **待装的行与已装的行一样由服务器渲染**，因为目录是用户会编辑的文件；只有按钮是脚本的事，没有脚本的按钮是页面兑现不了的承诺。安装与刷新在服务器上是同一件操作——`installer::install` 两种情况都写文件，用 `replaced` 说明发生了哪一种——所以两个按钮共用刷新那条队列与轮询，而不是各长一套副本；结果句用的是被按下的那个词。
- **写下了文件的刷新，会让页面把这一区重新读一遍**（`实现中决定`，2026-11-04）。被按下的那一行写着「in the catalog, not installed here」，摘要里还数着两个列表，而一次安装把这几句全都改了 —— 页面停在原样，就把一次成功的安装显示成一次什么也没发生的按压。脚本因此从重新取回的页面里整段取下这一区，而不是自己改那几句话（那会成为同一批事实的第二个出处）；换掉的也只有这一区：对话框当初不得不放弃整页刷新，正是因为整页刷新会连对话一起带走，而一个打到一半的应用名是同一个损失，只是隔了一页。
- **读不出来的目录行，就报在「不可用的 skill」旁边。** 同一个事实往上抬一层：一条无声消失的条目，与一份从来没有过它的目录，读起来一模一样。

**release 比对已落地，请求走它自己那条缝**（`实现中决定`，2026-10-31）。`crates/skills::release` 回答一个问题：「盘上这份的版本，比包里发布的最新版旧吗？」—— 一次请求、一次比较 —— 而请求走的是 `Releases` 这条缝。它返回的是答复的**本体**，不是解析好的 release，理由与 `Publisher` 返回程序的 stdout 相同：本体能出的每一种错，都在测试用一个字符串就能驱动的代码里判定。那条缝底下的 socket 此后已经接上，接在哪、带出什么决定，见后面单独一段。`release_url` 把端点写进契约，后来那条传输层因此没有形状需要自己发明。五条决定：

- **`GET` 没有从模型客户端借，也不需要借。** 缝是本 crate 自己的，返回 `io::Result<String>`、收一个 `owner/name` —— skill 的问题用 skill 的词表，这正是当初刻意不复用模型客户端那条 `POST` 缝时答应的事。
- **四个答案，因为「没有」与「说不准」不是同一个答案。** `UpToDate`（无事可做）、`Newer`（刷新，并把采纳的版本记下来）、`Unknown`（最新版知道了、盘上那份没记录 —— 一次刷新把它采纳下来，从此可比）、`CannotTell`（附一个 `Why` 点名缺的是哪一块）。把第四种并进第一种，就是更新检查悄悄不再提供更新的由来；它也是让一条坏掉的检查读起来不像健康检查的那一支。
- **版本是可选 `v` 前缀之后的点分数字，三种形状宁可拒绝也不猜。** 日期标签（`2026-10-31`）当数字比就是 `2026 > 1`，按日期打标签的仓库会因此每次检查都提供一次「更新」；预发布版本要一整套自己的排序规则，猜错的代价是把人更新到他没要的 beta；而状态文件里记录的版本被同一套规则拒掉，那就是有人手改过的文件。三种都得到「不更新」，这就是安全的方向 —— 手动装仍然可行，而 `CannotTell` 会把话说出来。
- **比较逐段按数字，短的一侧补零。** `0.9` 比 `0.10` 旧 —— 按字符串比结论相反，而这个 bug 要到第十个发布才现形。`1.0` 等于 `1.0.0`。比已装版本**旧**的 release 不算更新：有人从分支装过时，状态文件可以领先于最新 release，往回退是没人要求的降级。
- **用户自己带来的 skill 在问网络之前就被拒。** `managed` 是 `state` 里的闸门，这里先查它，因为一个任何更新都不该碰的文件没什么可问的。检查收的是 `Option<&Installed>` 且容忍 `None`，调用方换个参数形状也够不到非 managed 的文件。

**装的时候为什么不记版本，版本又从哪来。** `<program> skill` 对「我发布的是哪个版本」一个字都不说，所以 `installer` 只记出处、把 `version` 留空，而不是编一个后面整套比较都要依赖的数字。版本只有一条路知道：release 检查去读包里发布的那个，而 `Newer` 与 `Unknown` 正是 `adoptable()` 会给出值的那两种 —— 一次刷新采纳它，再经 `record_update` 记下。这一片之前装下的那些 skill，也正是靠这条路在第一次刷新后变得可比。

**此后落地的第三片：安装本身**（`实现中决定`，2026-10-31）。`installer` 驱动目录所描述的那一个副作用——对 `install: self-publishing`，跑那个包、收下它打印出来的 skill 文件——并把结果记下来。五条决定随之定下：

- **发布者是条目自己的名字，不是一个常量。** 参照实现对每个条目都设同一个 `CLI_NAME`，于是第二条目录条目会去跑第一条的程序（`实现自决, ref: emrg/skills/installer.py`）。这里用条目自己的 `name`；跑不起来时，拒绝里点出这个名字以及它来自哪个仓库——仓库地址就是修法，而这是拒绝欠读者的东西。
- **deepnest 没写过的文件永不被覆盖，而来源的两半都要查。** 状态文件说这个文件是不是 deepnest 放的，磁盘说这里到底有没有东西；任取一半都足以弄丢别人的工作，因为状态文件可能缺失、文件也可能被删。状态文件记成「用户的」那个名字，哪怕路径是空的也拒绝；状态文件没有记载、而文件已在盘上的，按来源不明拒绝——和缺 `managed` 字段同一个读法。参照实现是直接覆盖 `dest/<name>.md`。
- **发布出来的头部必须声明目录要的那个名字。** 参照实现按*发布出来的*名字写文件、按*目录的*名字记状态，两者随即不一致，更新循环于是去找一个并不以那个名字存在的 skill。这里名字不一致就是一条点出两者的拒绝。
- **不在盘上的不记账。** 先写文件、后写状态，所以中断的安装留下的是一个没记账的文件——下一次安装会拒绝覆盖它，这是安全的方向——而不是一条指向空气的 managed 记录。`install` 只改内存里的状态，落盘由调用方做，这样本 crate 写文件的地方仍然只有一处。
- **版本不编。** 参照实现在 release 检查失败时记 `version: "unknown"`；状态模型对「来源没说」已有更好的答案——字段缺席——而刷新时保留原有版本，而不是把它清掉。真实版本来自 `release` 的那次检查，那是唯一学得到版本的地方。

`Publisher` 是 trait，理由与 `Runner`、`Spawner`、`Probe`、`Prober` 相同：值得测的每一条拒绝都发生在程序跑完之后，而跑真程序的测试量到的是那台机器上那个程序的行为。真的那个会一直等到包的进程结束——这是要说明的限界，而它的修法落在这道缝后面，不落在逻辑里。

**由 agent 发起的那条安装后来才落地，和它所依赖的提权提示一起**（`实现中决定`，2026-11-01）。安装是对用户机器的副作用：它写到应用目录之外，还可能覆盖用户改过的文件，正是悬浮球该问一声的那类动作 —— 所以这个工具和那个提示一起落地，不抢在前面。先落地的是**人**主动要的那一版：`POST /api/skills/refresh` 由面板自己的按钮发起，按下去的人就是那个提示本来要取得的同意，所以它是一条独立的路由，而不是一个轮次能调的一步。**agent** 要的那一版是 `install_skill`：工具的说法在 `crates/tools/src/skill.rs`（和 `subagent` 一样是一条缝），接线在 `crates/deepnest/src/install.rs`。它是一次**天生的**提权请求而不是靠策略判出来的 —— skill 装在 `~/.deepnest/skills/`，那不在三个可写根里 —— 所以在 `workspace-write` 下这次调用按策略自己的话被拒，并点名够得着的那个模式；同一次调用带上 `request_mode` 再发，只在那个人批准了这一次放宽之后才跑。那条接线同时也是 `install` 那笔债的还款处：它的模块 doc 说谁接上真发布器就欠它「一个 worker 或一个超时」，面板用 worker 还了，轮次用死线还（`SpawnerPublisher`，跑的就是 `bash` 用的那个 `Spawner`）。

**此后落地的第四片：那条缝底下的 socket，以及面板读的那条路由**（`实现中决定`，2026-11-01）。`Releases` 由 `crates/deepnest/src/updates.rs` 实现在 `crates/gateway` 的 `get` 之上，而且它落在这儿、不在 `crates/skills`：这个 crate 是唯一同时依赖两边的那个，于是缝自己的 crate 保持零传输——这正是它模块 doc 要的，也是它无网络可测的原因。接线带出三条决定。

- **端点是参数，不是字面量。** `release_url` 仍是默认值，因为那条 URL 是契约的一部分、并且自己有形状测试；但一条只够得着 `api.github.com` 的检查，是任何测试都驱动不了的检查，而诚实的替代只有两个：一个证明不了传输的假缝，或一个量 GitHub 的测试。`Github::at` 与 `TlsHttp::with_connector` 是同一个决定：把测试必须控制的那一样开成参数。
- **不是 `200` 的状态是错误，绝不是空本体。** 空本体会以 `NotARelease` 落到 `release::check`——话对但含糊；而 `404` 是一个有真实含义的真答案：这个仓库没发布过 release。当错误报出来它落进 `Why` 的 `Unreachable`，细节就是那个状态码，人能读懂。
- **渲染页面的过程中永不发这条检查。** `report` 由面板脚本自己取的那条路由调用，绝不从同步的 skills 报告里调——后者读盘并渲进标记，在那个路径里塞上每个 skill 一次 TLS 请求，会让一台断网的机器挂住它本该打开的面板。

**此后落地的第四片：对答案动手的刷新**（`实现中决定`，2026-11-01）。`crates/deepnest/src/refresh.rs` 先调 `installer::install`，文件落盘之后再调 `release::check`，把 `adoptable()` 给出的版本经 `record_update` 记下并写出状态文件。这是 `install` 有史以来的第一个调用方。四条决定随之定下：

- **刷新是入队即返回。** 真发布者是那个包、而且没有超时，等它的 `POST` 会为别人的程序占住一条连接。路由回 `202`，自有线程干活 —— `crate::rebuild` 已经是这个形状 —— 页面轮询同一条路由取结果。
- **一次只跑一个，且是拒绝而不是排队。** 状态文件是一个文件：两个写者各自读、各自记自己的 skill，后写的会悄悄丢掉前一条记录。一次在跑时再问回 `409`，并点名在跑的是哪个。
- **先文件，后版本。** `install` 不记版本、只保留原有的，所以版本只能来自那次检查 —— 而它在重写**之后**才问，因为文件才是用户要的，一个答不上来的 forge 不能把它取消掉。检查答不上来时，刷新照样成立、版本保留原值；原本没有就仍旧没有。
- **这是用户的刷新，不是 agent 的。** 那个按钮就是提权提示本来要取得的同意，所以它可以先于提示落地。轮次要够到 `install`，只有走 `install_skill`，而且只对那个人放宽过的那一次调用。

### `crates/apps` —— 应用生命周期

模板、编译、启动、停止、重启、日志、端口分配。模板注入 **WAL + `busy_timeout` + 单写者约定**，不交给每个生成出来的应用自己决定 —— 实测里第二写者在 `timeout=0` 时立刻失败，`busy_timeout=5000` 时等 1817 ms 成功。

前端用 bun 打包，**不做 HMR**。刷新由「这一版完成」信号触发，绝不由文件变更触发，否则会刷出半成品页（`宿主 18:49`、`实现自决`）。

模板同时钉住转发层契约：资源引用用相对路径，应用必须能跑在路径前缀下。

**已落地第一片：目录契约**（`实现自决`，2026-10-31）：slug 校验取目录名与 URL 段两个命名空间的并集；目录是不是应用由 `deepnest.toml` 说；发现必须连「跳过原因」一起返回；日志尾部按字节截到 64 KiB。

**已落地第二片：进程生命周期**（`实现自决`，2026-10-31）：端口、监督器、启停。四条决定 —— 端口每次启动现分配、不持久化（存下来的端口一旦被别人占走就成了要维护的谎）；「启动成功」＝**端口有人应答**，不是 spawn 成功（生成出来的应用最常见的死法是启动时缺库或绑不上端口）；spawn 与 probe 都是 trait 缝，状态机加超时才能靠假件测；停止一个没在跑的应用算成功（调用方的意图是后置条件），重启是「停再启」而不是发信号（新端口不能让上行的撞下行的）。

退出路径（`实现自决`，2026-11-01）：停止请求 —— Ctrl-C、`kill`、关闭控制台窗口 —— 由一个只做一件事的处理器记下：置一个标志位；等这个标志位的那个线程**先关监听、再停应用**，因为请求正是启动应用的来源。监听的关闭是有界的，一条不说话的流不能把退出挂住；应用在它之后一个个停；进程随后以 `0` 退出，因为被听见的停止不是失败。这段序列在 `crates/deepnest` 里、紧挨它要收下去的监督器 —— 不在 `crates/gateway`，那一层只管门、不认识应用。处理器听不到的是 `SIGKILL`：那样被杀的 deepnest 仍会把应用留在那里跑，那也是唯一一种只能靠 pid 找到应用的场合。

**已落地第三片：模板与编译**（`实现自决`，2026-10-31）。`create` 写文件、`build` 跑工具链，分成两步而不是一步，因为两者**失败的样子不一样**：写到一半停下留下的是「不是应用的目录」，重跑一次即可；编译失败留下的是完好的源码树加一个说「不行」的工具链，对用户唯一有用的是**哪一步**和**它的输出**。

创建侧四条决定：

- **manifest 最后写。** 它是「这个目录是应用」的判据，所以半途失败留下的是一个**不是应用**的目录 —— 这是真话，也把「再创建一次」摆成了修复方案。先写 manifest 会留下一个被列出但源码缺失的应用，读起来像坏了，并把用户指向一个他从没见过的文件。
- **非空目录绝不覆盖。** 应用目录里是用户的数据、数据库和 agent 的对话，没有撤销。覆盖掉会是这个程序能做出的最具破坏性的事，所以它拒绝，并说出拒绝的是哪个目录。
- **slug 与显示名是两个名字，不互换。** `Smoke & Test` 是个好名字，但它不是 Cargo 包名、不是目录名、也不是 URL 段。slug 就是目录契约已经校验过的那个机器名；显示名只出现在 manifest 与模板写出的 HTML/JSX 里。第一版把 `Cargo.toml` 的 name 填成了显示名，编译器当场拒绝 —— 一次真编译抓到了读多少遍模板都看不出来的东西。
- **二进制路径是一个常量，两边都点名。** `process::EXPECTED_BINARY` 是 `target/release/app`，模板的 `Cargo.toml` 就把 `[[bin]]` 声明成 `app`，正是为此。**一边改了是重命名，两边悄悄改了是监督器去找一个不存在的文件**，所以各自在注释里点名对方，测试断言两者一致。

编译侧三条：

- **计划是数据，不是 shell 脚本。** 步骤以（目录、程序、参数）的列表返回。生成一个 `#!/bin/sh` 会少写一行，但不可测，而且是为「不是这个平台跑的那个 shell」写的。
- **前端先编。** 这个顺序对链接不承重（服务端按请求读 `frontend/dist`），选它是为了：前端就失败时，已经不用再花一分钟去编 SQLite。
- **「成功」＝二进制在那儿。** 退出码只说明工具链满意；监督器的契约是一个路径，编译报成功却没有那个文件，下次启动会变成「还没有编译过」，离真正的原因又隔了一步。

**新应用还带一个整条回路的可跑示例**（`实现自决`，2026-11-03）。`src/deepnest.rs` 是应用自己的 agent 客户端：一个 `ask` 发出回合、在本进程里跑掉每一条交回的调用、把答案 POST 回去、返回文本；`src/main.rs` 声明一个工具（`list_items`）并把处理器放在旁边，并应答 `POST /api/ask`。三条决定：

- **声明与处理器在同一个文件。** 模型被告知有这么个工具、却没人能跑它，比没有这个工具更糟；把两者分开的模板就是在教那个形状。
- **`paused` 是被处理的分支，不是一句注释。** 这里唯一会写错的就是把回合当成一个请求。示例在交回上循环，因为「编得过、然后在第一个需要自己数据的问句上挂住」的客户端，正是这个文件要防的东西。
- **它是真编译过的，不只是读过。** 生成一个应用、离线编译、看有没有警告，这就是验证（实测：11 秒，零警告）；测试套件只断言文本，理由和它不编译一样：一个三平台都要 C 编译器的测试会因为与本代码无关的原因变红。

**把生成的应用真跑起来，才抓到它的第二个 bug。** `bun build` 只写出 `frontend/dist/main.js`，`frontend/index.html` 还留在模板放它的地方，于是只服务 `dist` 的服务端**每个资源都应答、唯独页面本身 404**。现在服务端先找 `frontend/dist`、再回落 `frontend/`。模板对契约（相对路径、容忍路径前缀）是对的，对「打包器把页面放在哪」是错的 —— 这正是编得过测不出的那类错，跑一次就现形。这次验证是**一次性**的（生成、编译、发几个请求，然后删掉），不留在测试套件里：一个三平台都要 bun 加 C 编译器的测试，会因为与本代码无关的原因变红。实测数字：2.1 MB 落在 `target/release/app`，约 31 秒。

没有应用的安装连 `apps/` 目录都没有，列表把这报成「还没有」，而不是故障。`crates/apps` 到此就是完整的：目录契约、进程生命周期、模板与编译。

**删除是这个 crate 的第五件事，也是唯一一件没有撤销的**（`实现自决`，2026-11-03）。`POST /api/apps/<slug>/delete?confirm=<slug>` 先停应用、撤销它的进程票据、清掉重建状态，再删目录。四条决定：

- **由调用方点名它要销毁的东西。** 确认放在请求里（`?confirm=<slug>`）而不是只放在面板上，因为表单重复提交、刷新的标签页、随手猜出的 URL 发来的都是一个光秃秃的 `POST`，而光秃秃的 `POST` 什么也不删。面板仍然先用原生 `confirm` 问一次 —— 两者不是替代关系，是同一个问题的两半，而服务器这一半点不穿。
- **先停进程，停不下来就是答案。** 在跑着的二进制下面删目录，会留下一个往不存在的路径写、还占着端口替一个已经不存在的应用应答的进程。
- **这个应用的票据和在飞行的回合都随它一起死。** 否则票据会比它开的路活得久，而一个还在跑的回合会往一个父目录正在被删的文件里追加转录。两者都在这里撤销，而不是留给以后去失败。
- **`crates/apps::remove` 拒绝三种东西**：符号链接（删一个符号链接，在不同平台上是删链接或者删目标，这事不赌）、普通文件、以及根本不存在的名字 —— 对一个从来没存在过的东西说「已删除」，是用户会据此行动的一句假话。它回的是条目数和字节数，因为这才是确认能诚实说的东西。

页面上 `delete` 是四个动词之外唯一的控件：那四个可以重来，这个不能，所以它在行的最后、也是唯一会先问一句的。它是染色而非填充 —— 一块实心红按钮会让最具破坏性的动作成为眼睛最先落到的东西。

以上都**不做**一件事：后台编译，或编译时汇报进度。编译占住发起它的那条线程 —— 面板自己的那个标签页在等，这本就是同步请求的意思 —— 而门外其他请求照常。要**边编边往那个标签页**报进度，那是一条流式响应，而转发层现在有了。

### `crates/gateway` —— 唯一的门

§2 描述的那个路由。最难的不是路由，而是**不对应用撒谎**：头重写、流处理、WebSocket 升级要透明到普通 axum 或 Express 应用在 `/app/<slug>/` 下不改一行就能跑。

**已落地：转发本身，以及它底下那层 HTTP**（`实现自决`，2026-10-31）。`/app/<slug>/…` 送到应用的回环端口，而应用被告知它就服务在 `/` 上。五条决定：

- **只摘掉前缀，别的都不动。** 应用看到的是 `/api/items`，它永远不知道自己活在 `/app/notes` 下。这正是普通应用能不改一行就跑的原因 —— 它写的是 `/api/items`，到的也是 `/api/items`；也正因如此，生成模板里「相对路径」那条才是契约。
- **应用看到的 Host 是它自己的端口。** 否则照 `Host` 头拼绝对 URL 的框架会把浏览器送回面板的端口，而同一个路径在那里是完全不同的意思。
- **页面被注入一个 `<base href>`（除非它自己声明了）。** 没有它，`/app/notes` 与 `/app/notes/` 会把相对路径 `./main.js` 解析成两个不同的地方；有了它，结果与地址栏怎么拼写无关。已经自己声明 base 的页面是**对自家 URL 做过决定**的页面，转发层不推翻它。
- **只重写 `Location` 与 `Set-Cookie`，其余一律原样过。** 指向 `/login` 的重定向不重写就会离开前缀、落到 deepnest 自己的 404；`Path=/` 的 cookie 会被发到这个端口的每一条路由（包括面板的 API），所以要把 cookie 关进前缀 —— 没有 `Path` 的要**补上**，因为浏览器默认就是 `/`。其余头原样透传：连自己都不理解的头也去改的代理，会把本该护着的应用改坏。
- **chunked 的 body 要解码，不能带着框转发。** Node 或 axum 应用对没量过长度的页面会用 `Transfer-Encoding: chunked` 作答；把头剥掉、字节留着，等于把每个分块的长度当正文交给浏览器。

**回答不一定是一个 body**（`实现自决`，2026-10-31）。WebSocket 升级与 SSE 流都从一个头开始，然后一直持续到用户离开，所以转发给出两种东西之一：一个完整的响应，或者应用的那条连接本身 —— 字节到多少就转多少。四条决定：

- **只凭脑袋定，不看 body。** `101` 是隧道，`text/event-stream` 是流；两者的 body 都没有结尾，想读到结尾来判断，就是读到浏览器放弃为止。
- **流式响应的头不做重写。** 它的 `Transfer-Encoding: chunked` 是后面所有字节的框，所以原样送出。上面那些重写属于**有 body** 的响应；永不完结的 body 没有 `Location` 或 `Set-Cookie` 可挪，而这一层自己编出来的长度会把流切断。
- **握手是唯一一种必须保住逐跳头的请求。** `Connection: Upgrade` 和 `Upgrade: websocket` 就是这条消息本身，不是关于消息的元数据 —— 应用收不到它们会回 `400` 而不是 `101`。所以握手整个透传（`Sec-WebSocket-Key`、`Sec-WebSocket-Version`、`Sec-WebSocket-Protocol`、`Origin`），唯一改的仍是 `Host`，理由照旧；也什么都不追加：加一句 `Connection: close` 就是在升级开始前把它结束掉。
- **隧道是拷贝，不是轮询。** 每个方向一条线程，各写各的 socket。单线程就得同时等两头，而升级后的连接恰恰两个方向都常常是闲着的。

**这逼着服务循环改了什么。** 一次一条连接对「答一个请求就关」的面板是合适的尺寸，对一条长开的 socket 就不合适了：accept 循环 —— 连同 token 心跳 —— 会堵在第一个打开长连接的标签页后面。现在每条连接一条线程，上限 64（超了按名字拒掉，不排队），而 `shutdown` 直接关 socket，不等一条永不完结的流。这一点的端到端检查就是「浏览器形状」的：一条什么都没发的空闲连接不许拖住下一个请求；一条已经升级的 `GET /app/notes/ws` 不许让 `GET /api/health` 答不上来。

**悬浮球在最后一跳注入，策略跟着它一起动**（`实现中决定`，2026-10-31）。`crates/gateway::dialog` 往应用的每一个 `text/html` 响应里加上悬浮球，并把应用设的 `Content-Security-Policy` 恰好放宽到球能加载为止。四条决定：

- **球是 deepnest 的，所以注入在 agent 够不到的地方。** agent 只要用户提一句就把应用页面整块重写，它写进页面的东西它也就能删掉。在转发这一层注入，球才熬得过每一次重写 —— 而球是用户看着应用页时唯一回控制面板的路。
- **没设策略的页面不替它设一条。** 没有 `Content-Security-Policy` 就什么都不限制，写一条上去只是白白拿走东西。改写是给设了策略的应用的，而设了策略的应用正是做对了的那一类。
- **不得不新增的指令，要带上 `default-src` 已经允许的东西。** `default-src 'unsafe-inline'` 且没有 `script-src`，本来允许内联脚本；回它一句 `script-src 'self'` 名义上放宽、实际是收紧。`'none'` 是替换而非并列：它只在单独出现时合法，和别的一起写，浏览器按忽略它来处理。
- **只有真的装上了球的页面才动它的策略。** 一个 `text/html` 响应如果本体里已经有球 —— 应用自己带了，或者经过了第二跳 —— 就原样保留它发来的策略。为没装上球的页面放松策略，就是白放松。

球自己的文件是 `crates/web` 的，由 `/dialog.js` 与 `/dialog.css` 提供，并且**它不带控制令牌**：应用自己的脚本与本页同源，写进应用页面的令牌就是应用读得到、花得掉的令牌。除此之外它不请求任何东西 —— 它显示的东西，要么在 gateway 写下的标记里，要么就是浏览器自己去加载的面板。

**消息框靠一张只够得着一条路由的通行证发出去**（`实现中决定`，2026-10-31）。`POST /api/apps/<slug>/chat` 要 `Authorization` 头，而球没有令牌可给 —— 给了它，应用自己的脚本也就有了。于是改成：服务应用页时铸一张 cookie（`crates/deepnest::grant`），路由只在那一条路上认它，别处不认。六条决定：

- **`HttpOnly`，因为这个值连它服务的那张页面都不该读得到。** 应用脚本与球同源，读得到的值就能被它抄进自己的请求，或者抄出这张页面。
- **`SameSite=Strict`，因为别的源不该花得掉它。** 别的站点的页面发不出带着它的请求，所以从别处点过来的链接或提交的表单，到这条路由时手上什么都没有。
- **`Path` 是那个应用的 chat 路由，不是应用的前缀。** 这与 `crates/gateway` 改写时关进 `/app/<slug>/` 的那张是不同的 cookie，差别正是重点：前缀限定的 cookie 浏览器根本不会附到 `/api/apps/<slug>/chat` 上，所以更窄的路径要自己一套格式，不能复用那一套。
- **放在内存里、八小时、且没有 `Max-Age`。** 会话 cookie，关掉浏览器就够了；时效在回来的路上把着，每次铸新的顺手剪掉过期的，而末端是点名的而不是沉默的：`401` 让球说出许可过期、让用户刷新页面，刷新就铸一张新的。
- **只有 `text/html` 的响应才配得到一张。** 球是注入进页面的，不是页面的响应里没有可发的框，为它铸的值是一张没人持有的通行证。
- **已经拿着一份可用值的页面不再给新的。** 每次加载都铸一张会把存储搅个不停，还会把第二个标签页的值交给第一个，所以请求里已经带着一张活着的通行证时就保留它。

这件事**没有**解决什么，直说而不留给人自己撞上：应用自己的脚本与本页同源，所以它能花掉这个应用的 agent 轮次 —— 页面归应用所有，这一点杜绝不了。它做不到的是：读到那个值、拿去用于别的应用、够到那一条以外的任何路由、改配置、启动或停掉任何东西 —— 没有一张通行证打开这些。

这一片**不做**的，逐条点名，因为每一条都是另一件活：

- **对应用不发 `POST`。** 一层从不读 body 的代码无法转发 body，而不带 body 转过去，等于对没见过内容的东西回了「已完成」。
- **流已经结束、浏览器却还赖着不放的连接会一直占着它的线程**，直到浏览器关掉 socket。上限就是 `MAX_CONNECTIONS`；另一条路是给空闲的 WebSocket 设超时，那会毁掉这一片存在的唯一一种连接。

转发是一个 `Forwarder` 缝，理由与 `Spawner`/`Prober` 一样：路由要答对的是**把请求送给哪个应用**，而测这个决定不该依赖内核恰好把督导者申请的那个端口交给一个真应用。

### `crates/web` —— 控制面板

**已落地**：面板本身 —— 端点状态与首启表单、应用列表（含「不是应用」的目录及原因）、新建应用、每个应用的五个动作、加载器找到的用户级 skill 与它拒掉的每一条（连路径和原因）、通往 `/app/<slug>/` 的 `Open` 链接。一张 HTML、一份样式、一段脚本：不上 CSS 框架、不上图标集、不上打包器 —— 需要构建步骤的面板，就是仓库里没人读得懂的面板。

应用页的悬浮球是本 crate 的字：`dialog.js` 画出球，`dialog.css` 把它与应用自带的任何样式表隔开（每条选择器都从 `all: initial` 起，为另一个页面写的 reset 遮不住它）。与 `crates/gateway` 的分工是刻意的 —— gateway 决定球**放在哪**、需要什么策略，那是改写；球本身是人点的页面，那是本 crate 的事。

**消息框已落地**（`实现中决定`，2026-10-31），走的是上面那张通行证：球打开一个带输入框、发送按钮和答案的面板。三件事它做对了：

- **答案是文字，不是标记。** 它是模型的输出，而一条拒绝的文案并不比一条回答更可信；盒子写的是 `textContent`，它请求的那个 slug 同理，被当目录名而不是代码。
- **每种失败都点名下一步。** 许可过期就说刷新（刷新正是铸新的那张），服务器够不到就说 deepnest 可能没在跑，被拒就把那条路由说的话报出来。盒子闷不吭声，用户就只能猜这三种里发生了哪一种。
- **仍然没有令牌。** 凭证是服务这页时给的那张 cookie。脚本既不读 `document.cookie`，也不碰面板的 `<meta>`，所以一个被自己的 agent 重写过的页面，同样没法从盒子里掏出令牌。

**球里的提权审批已落地**（`实现中决定`，2026-10-31）。一次一跳、逐次批准，批准它的那个人正看着这页。五条决定撑着它：

- **申请搭在需要那次更宽权限的调用上。** `request_mode` 与 `justification` 是工具调用的两个参数键，进工具之前就被读走并摘掉。另设一个工具等于「申请权限却不说为哪件事」，而多跑一个来回等于花一次模型调用去说这次调用本身已经说了的话。循环在问任何人**之前**先查跳表，所以不构成放宽的申请根本不会变成问题 —— 让人去批「把 workspace-write 放宽成 read-only」是在请他批准一次收窄，这种问题问够几次，他就不再读了。
- **轮次等，页面轮询。** `GET /api/apps/<slug>/escalation` 是消息在途时悬浮球问的那条；`POST` 同一条路径就是回答。等待有两分钟上限，超时回来的是「没人回答」而不是「不行」—— 模型下一步不同，用户该做的也不同。
- **一次调用，会话不动。** 批准只为这次调用的上下文产出一个 `Grant`；会话自己的策略只是被借用，从不被写，模型读到的工具结果两头都说清楚：这次调用跑在哪一档，会话仍在哪一档。
- **第二张 cookie，而不是放宽的那一张。** 页面本来就握着一张只指 chat 路由的 cookie；问题路由拿自己的值与自己的路径，所以「花掉一次 agent 轮次」的能力回答不了一条提权申请。一个值同时指明应用**与**路由，路由两样都查。
- **拒绝带上宿主的原话，批准一句都不带。** `Answer::Denied` 的文档写的是「他们的原话，若有 —— 给模型看，而不是转述」，而空理由正是让一次拒绝变得读不懂的原因：只被告知「不行」、没被告知为什么，而把 `Denied` 与 `Unanswered` 分开的全部意义就在于模型下一步不同。所以问题块里有一个写理由的字段，且是可选的：只想说「不」的人就只说「不」。这个键只在拒绝、且字段非空时才加 —— 批准只发 `{approve: true}`，因为 `Verdict` 拒收不认识的键，而批准没有东西要解释。该字段随问题一起清空，所以对一条申请写下的理由答不到下一条上去。

**转录是这一轮发生事情的顺序，不是一串调用**（`实现中决定`，2026-11-02）。记录里一直有「说了什么、调了什么、回了什么」，页面却把整轮的调用画成一份平铺清单、答案压在最下面，于是「说一句为什么、做、说一句发现了什么、再做」的模型，它那一轮的形状 —— 话、批次、话、批次、答案 —— 一点都看不见。宿主是在读一份转录时把这个规则说出来的：**每一条消息，把一批调用与下一批隔开**。由此有四件事，而它们是同一个决定：

- **一批折起来，而且折叠行说明它怎么结束的。** 同一轮的调用住在同一个折叠下，那行写着 `3 tool calls · 2 ok, 1 failed` —— 数的是各自的结局，而不是归纳成一个判决，因为「读了四个文件、有一个失败」两样都是。用的词就是行里的词，所以摘要与它所摘的那一行不会各说一套。
- **note 画在它发生的地方。** agent 会写下 note —— 为什么这一轮提前结束、什么没能跑；而一个把预算全花在工具上的轮次根本没有答案，没有 note 它就跟「从未跑过」长得一样。`history::Note` 带 `round`：写这条 note 时这一轮已经记下几次响应，编号与 `Call::round` 一致，**首个请求之前**写下的为 `0`。那个 0 就是全部要害 —— 压缩发生在轮次开始之前，而没有位置的 note 会被堆在五百个批次下面，读成最后发生的事。
- **一行调用由 intent 来读，由参数来审计。** 每个工具的 schema 都把 `intent` 列为必填，所以行首是模型自己说「想够到什么」的那句话；原始参数 —— 命令行、路径 —— 退到第二层折叠里（与答案在一起），以及行的 `title` 上（一行没有宽度装下的那件事）。加这个字段的接缝是 `registry::definitions`，**凡是不走它就拼出来的请求都不会发这个字段**：循环曾经直接从工具上读定义，于是没有任何模型被要求过，每一行都退回裸参数，而 registry 自己的测试对着一个没人用的列表照样绿。
- **窗口是这场对话的**（`#85`、`#112`、`#117`、`#118`）。面板 22rem 宽、最高 `78vh`，而一次交换 —— 带代码块的答案、产出它的那些调用、后面那句追问 —— 在只有 280 px 的窗口里本身就 365 px。`Expand` 把窗口交给它：用 `100vw` 与 `100vh` 而不是 `inset: 0`，因为经典滚动条要占掉布局视口 15 px，靠偏移量定的表格在每条 Windows 构建上都正好短那么一截，右边漏出一条应用。表格升起时下面的页面被按住不动 —— 一层不透明表格底下还在滚的页面，等于在看不见的地方把应用挪走 —— 做法是在 document 元素上加一个类，且由状态的两半（是否展开、是否在屏上）各自取下与交还，所以关掉面板一定会还回去。阅读宽度没有消失，它搬了家：表格的每个子元素都落在同一条居中的 44rem 栏里，于是散文还在原来的地方断行，而宽窗口换来的是表格与代码块要的高度。实测 1400×900 与 390×844：表格的盒子在四个方向上都等于视口，栏宽 704 px 与 390 px，滚动位置在加锁与解锁前后不变。`Esc` 一次退一级 —— 先退展开，再关对话框。

**面板其余的部件**（`实现中决定`，2026-10-31 → 2026-11-02），每一个都是「一轮在跑时、或跑完之后」人需要知道的一件事：

- **`Stop` 只在有轮次在跑时出现**，因为一个常驻的「停止」是没有对象的按钮。它在按下那一刻就说，而不是等回复到了才说：控件变成 `Stopping…` 并保持禁用，另有一行说明这次停止会够到什么 —— 有意思的正是「什么都还没发生」的那一刻。**它够到的是这一轮的两半**（`宿主报告缺陷，2026-11-03`）：正在跑的命令被杀掉；正在等的模型调用被放弃 —— 关掉流式读取底下的那个 socket，读取立刻返回，而不是等模型吐出下一个 token。在这之前，标志只在两次调用之间被读，于是调用进行中按下的停止只能等它自己结束 —— 在跑着的页面上实测，就是发送框锁死 27 秒，人没法在刚结束的工作自己跑完之前问下一句。够到的做法是一个看门线程拿着 socket 的克隆，每 50 ms 看一次标志（`crates/gateway/src/transport.rs::interruptible`）；阻塞中的读取自己什么都查不了，所以注意到的不是读取的那个线程。
- **`Conversations`** 在转录**之上**打开这个应用的会话列表，而不是替换它，所以人在离开之前能看见自己正要离开什么；当前所在那一行有标记。转录是从 `GET /history` 读回来的，而不是页面自己记着，所以刷新之后还是同一轮 —— 而且这个窗口只增不减，因为「固定最近二十条」不是这场对话的视图，而是把它开头悄悄删掉的对话。
- **附件按钮与屏幕截图**是同一张图的两种来路：一个文件，或者 `POST /api/apps/<slug>/capture`，给没有东西可粘贴的人。抓屏发生在本进程里，不在浏览器里 —— `getDisplayMedia` 每抓一次就要一个浏览器选择器和一次系统弹窗，而 deepnest 本身就是原生进程。它**故意不是** agent 能调用的工具（`crates/deepnest/src/capture.rs`）：抓屏是人在指着某样东西。
- **成本行**落在答案下面、比答案安静 —— `This turn: N tokens in, M out`，端点报缓存份时一并写出。它由回复自己的 `usage` 画出，没有就清空而不是猜。
- **七条路由，七张 cookie。** `chat`、`escalation`、`build`、`history`、`cancel`、`sessions`、`capture` —— 各自拿着服务这页时铸的值，各自限定在自己的路径上。所以一个能力命名的是**一条路由**，不是一个 API；残留风险就写在它产生的地方：应用自己的脚本能发同样的请求，于是能花掉它自己的 agent 轮次，但不能花别的应用的、够不到配置、启停不了任何东西、也读不到令牌。

### `crates/packaging` —— 单文件

zstd 压缩的工具链载荷首次启动**原子**解包 —— 先解到临时目录再改名，半套工具链永不被当成完整的。C 工具链不自带：首次编译前检查 Xcode CLT / VS C++ Build Tools 并引导安装。

**已落地：工具链的目录契约**（`实现自决`，2026-10-31）。`crates/packaging` 现在回答三件事：解包好的载荷住在哪（`~/.deepnest/toolchain/<version>/`）、什么算「能用」、以及被中途杀掉的解包会留下什么。随之定了四条：

- **临时目录是它将成为的那个目录的兄弟，就在 `toolchain/` 里。** 解到系统临时目录是最显然的选择，也是错的：那样「发布」就成了在用户 home 与临时目录不同卷时**跨文件系统改名**，而跨卷的改名不是改名，是复制加删除 —— 它被打断，留下的正是这个模块要防的那种「半套工具链」。
- **目录能用不是因为它存在，而是因为标记文件在。** `adopt` 在改名**之前**把标记写进临时目录，所以发布出去的名字只在内容齐了之后才出现；缺少标记的目录报为「被中断」且永不使用。`crates/apps` 用 `deepnest.toml` 做的是同一件事：一个目录是什么，由它的标记说了算。
- **标记记的是载荷，不是版本号。** 版本目录可以活得比填充它的那次构建更久 —— 两个开发构建都自称 `0.1.0`，备份还原也可能跨过一次升级把旧的放回来 —— 所以带着别的载荷的目录会被报出来并替换，而只比版本号会把它当成可用，让用户继续跑上周的编译器。
- **被中断的解包是扫掉，不是续上。** 一半的载荷不是能接着写的东西；拿到端口的那个进程在启动时清掉残留并逐个点名，因为端口就是单实例准入 —— 它正是「此刻没有别的 deepnest 在写临时目录」的证明。

**已落地：C 工具链预检**（`实现自决`，2026-10-31）。README 早就许下「首次编译前会检查并引导安装缺的东西」，现在这个承诺兑现了，落在 [`cc`]。随之定了四条：

- **答案是三种读数，不是布尔。** 「有」「没有」「这一检本身答不出来」是分开的，因为对应的动作不同：编译、装那个被点名缺的东西、或者去看看坏掉的探针。把第三种压成「没有」，就是让用户去装一个他可能早就装好的东西。
- **三种里有两种会拒绝编译。** 答不出来的一律 fail closed，与这个 crate 里其余读数同源：在「说不准」之上开跑，等于花掉用户一分钟，最后从一个编译器那里得到同一个拒绝，而那时说得更少。路由回 `412`，并说明一步都没跑。
- **macOS 问 `xcode-select -p`，不查固定路径。** 工具默认在 `/Library/Developer/CommandLineTools`，装整套 Xcode 又会在别处，`-s` 更能指到任何地方 —— 路径检查会对一台明明能编 C 的机器答「没有」，而错的「没有」会拦住一次本来能成的编译。同理，Windows 问 `vswhere` 而不是在 `PATH` 上找 `cl.exe`：不在开发者命令行里，那些工具从来就不在 `PATH` 上。
- **引导是一个能粘的命令或一个能打开的页。** 「装一个 C 工具链」不是引导，`xcode-select --install` 才是。这是承诺里关于用户的那一半，而一条测试守着每个平台的引导都可执行。

**载荷的写端也落地了**（`实现中决定`，2026-11-01）。`crates/packaging/src/pack.rs` 是 `unpack` 的另一端：一棵工具链树进去，它读的那种 tar-in-zstd 出来。没有发明任何新东西 —— 读端先写，它的形状就是规格 —— 所以四条决定讲的是**写端欠读端什么**：

- **出去的是流，不是 `Vec`。** 载荷是 deepnest 携带的最大一件东西，`pack` 若返回字节，就会在机器本来就忙的那一刻把整套工具链再在内存里存一份。writer 由调用方给。
- **同一棵树打包出同样的字节。** 条目排序、头部的时间与属主字段清零：否则按 `read_dir` 顺序、带各自 mtime 打出来的包，会让一棵没变的树每次构建都变成一个不同的归档 —— 而这个归档是要签名、要发布的，「载荷没变」必须是两次构建能达成一致的事。
- **读端拒绝的，写端先拒绝** —— 走读端自己的 `checked_link`，而不是把规则抄第二遍。读端必须拒绝逃逸链接，因为它看不见归档是谁打的；写端必须拒绝它，因为它看得见，而这是唯一一个「修法是构建脚本里一行」而不是「首次运行最后甩给用户一句他没问过的话」的时刻。fifo、socket、设备节点同理。
- **deepnest 自己解包过的树按它带的标记拒绝。** `adopt` 写 `payload`；带着它的归档会与下一次解包被告知要发布的 id 冲突，而 `adopt` 会无声地覆盖掉其中一个。把打包器指向 `~/.deepnest/toolchain/<version>/` 正是会产生这种归档的失误，所以拒绝句要点名那个文件。

硬链接按文件打包：它是同一份字节的第二个名字，要找出成对的得建一张本 crate 别处用不上的 inode 表。两种做法解出来的都是同一棵树。

**解包已落地。** `crates/packaging/src/unpack.rs` 把 tar 套 zstd 的流解进 `Staging`，再由 `Staging::adopt` 发布，上面这份契约一个字都没动。随之定下三条，针对的都是**坏载荷**能干什么，而不是攻击者 —— 归档由发布流水线的一步产出、另一步读取，这里防的是打包那边出错：

- **遇到坏路径就整体拒绝，不做修补。** 绝对路径、或用 `..` 往上爬的条目，让整个解包带一个点名的理由失败，而不是跳过或改写，工具链目录保持原样。这里不靠 `tar` crate 自带的 `unpack_in`：一条独立、失败即关且能给出打包者可用理由的检查，比静默跳过更值。
- **链接在创建处判定。** 符号链接是载荷「借个名字写文件」的手段，所以它的目标按其所在条目的深度做词法解析，必须留在工具链根之内。逃逸的链接从一开始就不存在于树里，后面任何条目都无法借它写到外面，逐条目判定因此足够。
- **载荷只造文件、目录和链接，别的都不造。** 设备节点、fifo、socket 一律拒绝：工具链里没有这种东西，而创建它需要解包不该持有的权限。

**归档住在二进制里，首次构建解包它**（`实现自决`，2026-11-01）。`crates/deepnest/build.rs` 把发布流水线产出的归档嵌进来，`crates/deepnest/src/payload.rs` 按上面那份契约把它解到 `~/.deepnest/toolchain/<version>/`，此后的构建先在那里找程序。四条决定：

- **没有归档的构建嵌一个空的，并且说出来。** `include_bytes!` 要求编译期就有一个文件，所以构建脚本总是写一个：`DEEPNEST_PAYLOAD` 指了就读它，没指就写 0 字节。CI 与开发构建什么都不带，而 `payload::embedded()` 返回 `None` 正是那个读数 —— 此后的构建照旧用机器的 `PATH`，而不是在一份它从来就没打算发布的坏载荷上失败。`DEEPNEST_PAYLOAD` 指了一个读不到的文件则**直接让构建失败**：一个本想把工具链装进去的打包者，不该从用户那里才知道自己没装成。相对路径按 **workspace 根**解析 —— 也就是 `payload/` 所在、默认值指向的那个目录 —— 而不是按 `crates/deepnest`：构建脚本的工作目录是它自己那个包，所以照字面读 `payload/toolchain.zst` 会读进 crate 里，发布流水线的首次运行就是这样失败的，而那个文件明明就在仓库根上。
- **解包发生在首次构建，不在启动时。** 启动已经是赢下端口、开始服务面板的那一刻，让每次启动都为一件用户可能永远走不到的事付账，是白花。它同时定下了 packaging crate 要求的次序：构建只由请求发起，而请求只可能在 bind 之后到来，所以不会有第二个实例来争那个暂存目录。
- **载荷里的程序在 `bin/` 下，而这个目录被前置进 `PATH`。** 是前置，不是合并：自带的工具链必须赢过机器上碰巧装着的那个，否则一个「自包含」的二进制会拿机器上那个版本去构建用户的应用。没有 `bin/` 的载荷则不动 `PATH`，而不是把它指向一个不存在的目录。
- **`Runner` 就是载荷与构建相遇的那条缝。** `payload::Toolchain` 实现的是 `crates/apps` 早就有的同一条缝 —— `StdRunner` 只多了一个 `path_prefix`，别处一个字没动 —— 所以拿不到工具链的一次构建，会把这件事报告成那一步自己的结果（就在用户正在读的地方），而不是一个「找不到命令」。

仍未做的是：**归档上的签名**。`codesign` 那一步本身已经落地（`crates/bundle/src/sign.rs`，见下），它向本仓库要的不是密码，只是一个「密钥已在钥匙串里」的身份 —— 那是流水线某一步的事。

macOS 签名并公证（`宿主 20:48`）。自带工具链里的每个 Mach-O 必须在**打包前**就签好，因为首启解包不会补签名，而 hardened runtime 下未签名的子进程会被拒。Windows 不签名（`宿主 20:56`）—— 首次运行 SmartScreen 会警告，README 与首启页面都如实说明，而不是教用户盲绕安全提示。

**二进制外面那层 bundle 也已落地**（`实现自决`，2026-11-01）。`crates/bundle` 在一个已经存在的二进制外面摆出 `Deepnest.app`，它自己的可执行文件 `deepnest-bundle` 就是发布流水线要调的那一步。它没有任何依赖，三个平台都能编译、测试都过，尽管只有一个平台会读 `.app` —— 布局不过就是建目录加复制一个文件，而一个连两个非 macOS 平台都无法背书的写出器，就是没人背书的写出器。四条决定：

- **只有两个文件，因为只有两个名字是承重的。** `Contents/Info.plist` 是系统读取「该启动什么」的地方，`Contents/MacOS/deepnest` 是它启动的东西。图标、本地化、内嵌框架都是可选的，而一个还没被需要就先写下的名字，是之后每个读它的人都得跟着对齐的名字。
- **plist 是文本，所以版本要转义，而系统读不了的版本直接拒绝。** `CFBundleVersion` 只接受点分数字，于是带字词的发版 tag 会在「改一行发布脚本就能修」的那一刻被点名拒绝，而不是产出一个人能装上、却公证不了的 bundle。
- **已存在的路径一律拒绝，绝不往里写。** 半个 bundle 看起来是完整的 —— 一个在两次写入之间丢了可执行文件的 `Contents/`，Finder 照样会提供「打开」。
- **可执行位是设上去的，不是继承来的。** 一个以 `0644` 到来的二进制，就是一个打开后什么都没有的 bundle，而系统自己拒绝 `exec` 它这件事，永远传不到人的耳朵里。

这个 bundle 是**未签名的**，磁盘映像则归 `hdiutil`：签名盖的是已经存在的文件，所以它在后面；而在一个只有单一平台才有的程序外面套一层 Rust，只会多出一件要维持正确的东西，换不来任何多出来的读数。

**一份签名要盖哪些文件，现在也是一个有测试的答案**（`实现自决`，2026-11-01）。`crates/bundle/src/macho.rs` 按文件开头的字节判定它是不是 Mach-O，再遍历一棵树把是的收上来。理由是：签名那一步漏掉一个二进制，不是构建报错，而是一个能装上、能打开、然后在用户机器上拒绝启动编译器的载荷。四条决定：

- **由魔数判定，每个文件只读八个字节。** 加载器读的也是同一个位置，所以别的一概不看 —— 不读 load command，不看 `LC_CODE_SIGNATURE`，也没有一门以后要补课的文件格式。
- **一个魔数有两种含义，靠后面的计数分开。** `0xcafebabe` 既是 fat 二进制的开头，也是 Java class 文件的开头，而工具链归档里不会只有二进制。它后面那四个字节，一边是架构数，另一边是 minor 紧跟 major 的版本号，两段区间不重叠：Java 1.1 是 45、今天是 65，而没有哪个二进制造出过 45 个架构。1 到 20 当作 fat 二进制，再往上就不动它。
- **符号链接跳过，不跟随。** 签名会顺着链接盖到目标上，所以跟一条树内的链接，等于用两个名字签同一批字节；跟一条出树的链接，则签了载荷并不拥有的东西。树里那个目标会以它真正的路径被找到。
- **顺序是排好的，读不了的条目是拒绝而不是跳过。** 排好，是为了同一棵树的两次签名日志能对差 —— 打包那边已经做过同样的选择；拒绝而不是跳过，是因为「读不到就不签」正是这个模块要防的失败，只不过它穿着一次绿色的构建。

它不签名，也不知道 `codesign` 存在，这是故意的：「给每个 Mach-O 签名」这件事里，**悄悄错**的是枚举这一半，所以必须能在两个根本没有 `codesign` 的平台上被检查。

**签名那一步也已落地，而且它不碰任何秘密**（`实现自决`，2026-11-01）。`crates/bundle/src/sign.rs` 接过 `macho.rs` 给出的清单，逐个跑 `codesign`，并在报告成功之前逐个验签；`deepnest-bundle --sign <dir>` 就是流水线要调的命令。五条决定：

- **身份是从 `DEEPNEST_SIGNING_IDENTITY` 读进来的一个名字，没有任何密码经过这个程序。** 证书与私钥由单独的一步放进钥匙串；一个进到程序里的密码就是进程表里的密码，而需要密码的设计，就是只能靠 `.p12` + 交互提示才能跑的设计。没给身份就点名拒绝，而不是产出一个看起来完整的未签名 bundle。
- **每个文件都带 `--options runtime --timestamp --force`。** hardened runtime 与安全时间戳是公证两道绕不过去的门槛 —— 在签名这一步失败，比几小时后在公证失败便宜得多。`--force` 不是为了覆盖：每个 arm64 二进制身上都带着链接器留下的 ad-hoc 签名，没有它 `codesign` 拒绝替换，于是不带 `--force` 的签名会在第一个文件上就失败。
- **每签一个就验一个，验不过整轮失败。** 「签了」和「签上了」是两个不同的断言，加载器读的只有后一个；不问的那一轮，会把「codesign 退出码 0 但签名并不存在」报成一次绿色构建。
- **一棵没有二进制的树是拒绝，不是高高兴兴地签过去。** 空载荷要么是目录给错了，要么是打包那边把内容丢了，而绿色的签名步骤是最后一次发现它的机会。
- **签名与验签都是缝合层。** 值得测的是决策本身 —— 签哪些、什么顺序、第二个失败时怎么办 —— 而这种测试不可能拥有一张证书。只有 `StdSigner` 需要 macOS。

本机用 ad-hoc 身份端到端实测过：`deepnest-bundle --sign` 找到 bundle 里的可执行文件、签完并验过，`codesign -dv` 报 `flags=0x10002(adhoc,runtime)`，对产物 `.app` 跑 `codesign --verify --strict` 判 valid on disk。**安全时间戳没有观测到**，因为 ad-hoc 签名不产生时间戳；它需要真的 Developer ID 身份，而那正是还缺的那一块。

## 5. 不许漂移的接口

三处边界占据了未来大半的返工成本，在此固定：

```rust
trait SandboxBackend {              // darwin | linux | win32 —— 启动时选定
    fn fence(&self, roots: &WritableRoots, cmd: &Command) -> Launched;
}

trait Tool {                        // 每个工具一个实现，拒绝形状统一
    async fn call(&self, args: Value, ctx: &ToolCtx) -> ToolResult;
}

struct MemoryStore { /* 条目 + 索引；正文永不进提示词 */ }
```

应用目录布局与 `/app/<slug>/` 路径契约同样固定：这两处之上坐的是用户的数据和用户的 URL，晚改就是一次迁移。

## 6. 施工顺序

一个周期一个模块，每个都带测试落地：

1. `crates/llm` —— 流式、重试、降级。
2. `crates/sandbox` + `crates/command_scan` —— 三档、三后端、一份策略源。
3. `crates/tools` —— 八个工具，全部走围栏。
4. `crates/agent` —— 循环、持久化、记忆。
5. `crates/deepnest` —— 二进制 + 三平台 CI 矩阵。排在应用生命周期**之前**：「这东西在三平台上到底能不能起来」要在答案还便宜的时候答掉。此后每个模块要么接进二进制落地，要么在 PR 里说明为什么不接。**它现在承载 agent**（`实现中决定`，2026-10-31）：`POST /api/apps/<slug>/chat` 用一个真·按应用 agent 跑完一个轮次，所以它下面那五个 crate 从一条消息就能碰到，而不只是从测试里。
6. `crates/apps` —— 模板、编译、生命周期、日志。**已落地**，三片：目录契约 → 进程生命周期（端口分配、启停）→ 模板与编译（`POST /api/apps/<slug>/create` 与 `/build`）。三片全部接进二进制。
7. `crates/gateway` + `crates/web` —— 唯一的门、面板、悬浮球。**已落地**：gateway 的转发、它底下那层 HTTP、WebSocket 升级、不缓冲的流式、面板、悬浮球注入与随之而动的 CSP 改写，以及球里的提权提示 —— 申请由调用携带、页面轮询取它、回答只放宽一次调用。二进制并发地服务连接，正是它让一个轮次能一边等、页面一边作答。
8. `crates/skills` —— 加载器、目录、安装器。**已落地**：加载器（两个根、两种布局、遮蔽、跳过报告、提示词摘要）、随二进制内置的目录、记录哪些 skill 可被刷新的 `.state.json`、自发布包的安装路径、带自己一条一次性请求缝的 release 比对，以及那条缝底下的 socket 均已落地——socket 就是 `crates/deepnest/src/updates.rs`，它的路由是 `GET /api/skills/updates`，面板脚本从那里读。**对答案动手**也已落地（本片）：面板的刷新按钮走 `POST /api/skills/refresh`，对每个允许刷新的 skill 调一次 `installer::install`，再由 `release::check` 的 `adoptable()` 经 `record_update` 把采纳的版本记进状态文件。agent 发起的那条安装也已落地：`install_skill`（`crates/tools/src/skill.rs`，接线在 `crates/deepnest/src/install.rs`）在轮次内够到 `installer::install`，并且是写应用目录之外的唯一那条路 —— 在会话模式下被拒，只在那个人放宽过的那一次调用里跑。这个 crate 当初要有的每一片，现在都落地了。
9. `crates/packaging` —— 载荷、首启解包、签名。**已落地，只差签名**：工具链的目录契约（载荷解到哪、什么标记让一个目录算完整、清掉被中断解包残留的清扫）、C 工具链预检并接进 `build` 路由（缺就回 `412`，一步不跑）、解包本身（`crates/packaging/src/unpack.rs`：tar 套在 zstd 流里，逐条目读取，任何路径与链接目标在写入之前先对着工具链根判定）、以及它的写端（`pack.rs`）都已落地。载荷**就在二进制里**：`crates/deepnest/build.rs` 嵌入它，`crates/deepnest/src/payload.rs` 在首次构建时解包，`payload::Toolchain` 作为 `Runner` 接进构建（`crates/deepnest/src/router.rs`）。剩下的是这份归档上的签名，以及以它为前置的公证。
10. `crates/bundle` —— macOS app bundle，以及给它们签名。**已落地**：在一个已经构建好的二进制外面摆出 `Deepnest.app`，执行者是 `deepnest-bundle`；`src/macho.rs` 遍历一棵树并指出其中哪些是 Mach-O 二进制；`src/sign.rs` 逐个签名并逐个验签（`deepnest-bundle --sign <dir>`），三块在三个平台上都有测试。缺的不是代码，而是钥匙串里的一个 Developer ID 身份，以及其后的公证 —— 那需要 Apple ID、team id 与 app 专用密码。

## 7. 不可让步

- 三平台后端从第一行抽象（`宿主 20:56`）。
- 沙箱三档且 OS 级围栏，提权逐次（`宿主 19:03`）。
- 应用目录布局与单端口路径契约（§2、§3）。
- 每个模块带测试落地。
- deepnest 是单个二进制；应用是目录（`宿主 18:55`）。
